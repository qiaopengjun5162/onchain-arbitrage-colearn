## 核心论点：资金费率不是自然读数，是平台按规则做的测量

> 资金费率不是市场自然涌现的读数，是平台按一套规则做的一次测量。规则里有几个可配置、会调整的部件，而我们默认它们是常数。

## 费率公式

主流永续大体一致：
```
F = 溢价指数的时间加权平均 + clamp(利率 - 溢价指数, 上下限)
```
**差异藏在平均值里**：采样点数 n = 结算周期长度 / 采样间隔

## 坑 1：结算周期是变量，不是默认 8 小时

- 不少平台按合约设定周期，还会在特定条件下**临时调整**（接口里专门的「结算周期小时数」字段就说明它会变）
- **费率历史接口通常只返回费率和时间戳，不返回周期** → 你按固定 8h 对齐历史序列，跨过一次周期调整就会错位
- 对我们的影响：Z-score 滚动窗口如果跨越了周期调整，mean/stdev 计算失真

## 坑 2：时间加权平均的权重函数不一定相同

- 至少两种：
  - 文档只说「时间加权平均」（形状未知，需自己测）
  - 显式线性递增：`(P₁×1 + P₂×2 + ... + Pₙ×n) / (1+2+...+n)`——**末尾采样点权重是第一个点的 n 倍**（8h/每分钟 → n=480）
- 行为差别：「结算前的偏离对最终费率影响多大」——权重后置的平台末段偏离占主导，跨平台不能沿用

## 对 funding_sentinel_v2 的修正建议

1. **跨平台横向比较要小心**：各所结算周期/权重形状不同，`z-score` 是同所内标准化（OK），但 `OI 加权合成全局 funding` 是把不同口径的测量值加权——权重形状未知时合成值有偏差
2. **历史序列对齐**：拉历史 funding 时确认结算周期（okx/bitget 都是 8h 默认，但应核实近期有无调整）
3. **文档只读不如下单前实测**：对要实际交易的合约，先拉它自己的 config（结算周期/权重/上下限）

## 方法论价值

- 「默认它们是常数」——做量化第一课：**每个输入都要验证它是不是常数**（与我们「把看不到的部分显式列为未知」同构）
- 数据口径问题优先级高于策略逻辑：结论不稳定先查口径，别先怪情绪
